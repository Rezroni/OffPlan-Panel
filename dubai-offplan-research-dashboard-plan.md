# Dubai Off-plan Research Desk — план реализации v2

**Дата:** 24 сентября 2026. **Владелец:** Mokhamed. **Статус:** спецификация для реализации, переработанная после двух раундов вопросов.  
**Назначение:** закрытый рабочий дашборд одного агента; исследование off-plan, контент в Instagram RU/AR, персональные PDF для клиентов.  
**Важное:** реальные ответы API пользователя и документы конкретных объектов ещё не исследованы. Возможности, зависящие от полей и качества этих ответов, ниже явно условны. Примеры сумм вымышлены.

## 1. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| География | Только Dubai на первом этапе. Abu Dhabi — самостоятельное расширение с другими источниками. |
| Продукт | Внутренний дашборд, без публичного каталога и SEO на старте. |
| Объекты | Off-plan квартиры: Studio, 1BR, 2BR, 3BR. Виллы, таунхаусы, гостиничные инвестиционные продукты и коммерция вне MVP. |
| Целевой бюджет | Цена квартиры 1,5–5 млн AED. Полные затраты на приобретение показываются отдельно. |
| Покупатель | Планирует перепродажу до сдачи или аренду после сдачи. Качество жизни/района важно для привлекательности объекта; отдельный режим покупки для себя пока не приоритет. |
| Капитал | Ориентир первоначального взноса — 20%, плюс отдельные средства на сборы. Клиент должен иметь реалистичный план всех последующих платежей. |
| Исключение | Клиенту только с 20% и без возможности продолжать платежи инвестиционная рекомендация не формируется. |
| Горизонт | До сдачи, независимо от её срока. В подборе срок показывается, но фиксированного лимита 18/24 месяца нет. |
| Сравнение | Альтернативы в том же районе, в других районах с тем же бюджетом, похожие проекты ближе к сдаче. |
| Работа | Либо открыть известный проект, либо задать бюджет/цель и получить подбор. |
| Уточнение предложения | Полный Excel/план оплаты/условия уступки запрашиваются у представителя застройщика после появления заинтересованного клиента. |
| Контент | Два Instagram-аккаунта: русский и арабский. Рилсы около 60 секунд, иногда длиннее; графики поверх видео с автором. |
| PDF | Персональное сравнение 2–3 подходящих вариантов под бюджет и график финансирования клиента. |
| Приоритеты выбора | Возможность выхода → цена входа относительно альтернатив → нагрузка платежей → качество квартиры/района. |
| Ограничения ресурсов | Один разработчик с AI, до 30 ч/нед, до 200 AED/мес дополнительных расходов, существующий VPS + Coolify. |

20% не зашивать в каждый проект: если фактический план требует 10%, 25% или 30%, использовать подтверждённый график. После сдачи обязательные платежи post-handover тоже проверять, если они есть; горизонт анализа не отменяет договорных обязательств.

## 2. Что считать хорошим результатом

Дашборд должен позволять ответить на пять вопросов:

1. Для какого покупателя и при каких условиях этот вариант предпочтительнее альтернатив?
2. Чем обосновано ценовое сравнение и насколько сопоставимы объекты?
3. Сколько денег и когда реально понадобится, включая вариант «продать не получилось»?
4. Когда уступка допустима и что происходит с результатом при другой цене/сроке продажи?
5. Какие утверждения можно показать в видео/PDF, а какие требуют проверки?

«Лучший» означает лучший из рассмотренных подходящих вариантов при заданных критериях, а не лучший на всём рынке. Всегда показывать охват: сколько проектов найдено, сколько проверено, сколько исключено и по какой причине. Если удачный вариант не найден — сообщать об этом, не заполнять PDF искусственными рекомендациями.

Не строить продукт вокруг обещания гарантированной недооценённости или точной даты продажи. Строить воспроизводимое сравнение, оценку пригодности и сценарии с доказательствами. Проверяемая прогнозная модель может появиться позднее как отдельный модуль.

## 3. Два рабочих процесса

### 3.1 Research → Reel: до обращения клиента

1. Импортировать каталог обнаруженных проектов из разрешённых источников; пользователь также может добавить проект вручную.
2. Открыть проект или задать бюджет, комнаты, цель, район/допустимые районы.
3. Связать проект, фазу, башню и застройщика с официальными идентификаторами.
4. Подтянуть исторические сделки, готовые аналоги, доступные сведения о строительстве и окружающих проектах.
5. Собрать три группы сравнений: ready; off-plan близкого срока; off-plan ближе к сдаче.
6. Проверить происхождение исходной цены: цена «от» всего проекта не должна автоматически становиться ценой квартиры 2BR.
7. Выбрать тему: отличие цены, платежная нагрузка, близость к сдаче, риск конкуренции, сравнение двух районов.
8. Зафиксировать версию анализа; подготовить один сценарий и 1–3 графика RU/AR.
9. Просмотреть утверждения и экспортировать графики. Запись/монтаж делать вне дашборда.

Полный пакет от застройщика для этого процесса необязателен. Но если нет цены именно для нужного типа/площади, не выдавать точный AED/ft² и «скидку» для этого типа. Можно подготовить обзор района/позиционирования с явно указанными пробелами. Новое обнаружение в API — `first_seen`, а не доказанная дата запуска.

### 3.2 Client → Verified offers → PDF: после обращения

1. Создать клиентский brief: бюджет квартиры, доступные деньги, будущие пополнения по датам, резерв, цель, комнаты, районы, ограничения.
2. Получить предварительный shortlist из 5–10 проектов; это кандидаты для проверки, не готовые предложения.
3. Выбрать 3–5 кандидатов и запросить у представителей застройщиков актуальные материалы. Дашборд генерирует текст запроса; отправляет его агент вручную.
4. Загрузить Excel/CSV/PDF или вставить текст сообщения с датой и источником.
5. Подтвердить распознанные лоты, площади, цены, графики, сборы и условия уступки.
6. Проверить платежеспособность клиента по каждой дате и соответствие стратегии выхода.
7. Выбрать 2–3 подходящих варианта. Если подходит только один — показать один и объяснить отказ по другим.
8. Утвердить сравнительный вывод; сформировать PDF на зафиксированных данных; проверить и отправить вручную.
9. Сохранить отправленную версию и вопросы клиента. Новые данные создают новую версию, не меняют старый PDF задним числом.

Квалифицированный клиент для этого процесса — человек с бюджетом, целью и понятным планом финансирования, а не любой просмотр рилса.

## 5. Источники: что реально можно автоматизировать

| Источник | Использование | Ограничение, которое отражаем в модели |
|---|---|---|
| `dld_transactions-open` | Зарегистрированные продажи, цена/площадь, объём, даты | Это не доступные сейчас лоты; не смешивать продажи, ипотеки, дарения, земли и целые здания. Поля/ключи сверить в реальном API. |
| `dld_rent_contracts-open` | Арендные аналоги готовых квартир | Годовая аренда, новые/продлённые договоры, один/много объектов; регистрационная дата не равна началу договора. |
| `dld_units-open` | Характеристики единиц и поддержка связей | Не считать количеством непроданных квартир и не предполагать полный актуальный stock. |
| `dld_projects-open` | Идентификаторы, статус, ожидаемые сроки, прогресс | Текущая ожидаемая дата не является исходным обещанием или подтверждённой передачей ключей. |
| `dld_developers-open` | Юридические лица и идентификаторы | Маркетинговый бренд и юридическое лицо могут различаться; связи подтверждать. |
| `dld_oa_service_charge` | Расходы существующих аналогов | Точное имя набора уточнить; опубликован также `dld_oa_service_charges-open`. Нужны год, категории и единицы начисления. |
| `dld_residential_sale_index` | Потенциальный рыночный контекст после проверки условий | По умолчанию выключен для коммерческих расчётов: опубликованная страница DLD RPPI ограничивает такое использование. Условия конкретного API-набора проверить отдельно. |
| `docs.bayutapi.com` | Обнаружение проектов и обогащение, если использование разрешено | Сторонний сервис; тариф/квоты учётной записи неизвестны. Нельзя считать его официальным DLD или смешивать с `bayutapi.dev`. |
| Документы застройщика | Действующие лоты, скидки, графики, уступка, визуалы | Запрашиваются после лида, импортируются с подтверждением агента. |
| Ручная проверка/архив | Первоначальные сроки, фактическая передача, инфраструктура, особые условия | Каждому факту нужны источник, дата и охват. Не заменять отсутствие данными LLM. |

В проверенной документации `docs.bayutapi.com`: `POST /new_projects_search`, `POST /properties_search`, `GET /property/{property_id}`, `GET /locations_search`. Реальные поля и доступность проверять контрактными fixtures; отдельный endpoint подробностей проекта не выдумывать. В примерах есть amenities и координаты; наличие полного покрытия каждого здания не гарантировано. Публичные условия поставщика ограничивают коммерческое использование без письменного разрешения — подтвердить применение к вашему тарифу и задаче; наличие бесплатного ключа не решает этот вопрос.

Принцип источников по полю: официальная регистрация → DLD; действующая цена/наличие/уступка → подтверждённые материалы застройщика; маркетинговые особенности → источник с известным происхождением; итоговый вывод → ваша версия анализа. При конфликте хранить оба значения. Новый API-import не перезаписывает подтверждённое предложение молча.

## 6. Данные, интеграции и сопоставление

### 6.1 Первый технический шаг

Через сервер получить небольшие обезличенные образцы каждого набора: поля, nullable, единицы площади, примеры статусов и кодов процедур, ключи, фильтрацию, сортировку, пагинацию, квоты, даты изменения и охват. Ключи не запрашивать в чате: env на сервере. Создать `source_inventory.md`, `schema-map.json`, fixtures и адаптеры по источникам. Только после этого фиксировать внешние названия полей. Пользовательские API пока не проверены; в фазе 0 необходимо обнаружить реальные ограничения, а не имитировать успешную интеграцию.

### 6.2 Нормализация

- Денежные суммы хранить как `numeric`/Decimal; вычисления денежных потоков без потери точности JS float, округлять при отображении.
- Площадь: сохранять исходное значение, единицу и тип (внутренняя, общая, с балконом); отдельно нормализовать м²/ft². 1 м² ≈ 10.7639104 ft². Если тип площади неизвестен, помечать сопоставимость.
- Комнаты: Studio = 0; неизвестное = null, не 0. Служебные значения исходного справочника не интерпретировать по догадке.
- Идентификаторы источников хранить строками. Даты события, получения, публикации источника и ручной проверки различать.
- Удалять дубликаты только по проверенному ключу; если ключа нет, использовать задокументированную составную идентичность и отмечать неоднозначность. Не склеивать похожие, но разные сделки.
- Пустые значения не заменять нулями. Отсутствие цены/условия уступки — состояние данных, а не отказ застройщика.

### 6.3 Канонические сущности

Структура: master community → project → phase → building/tower → unit type → конкретный offer. Один маркетинговый проект может соответствовать нескольким DLD-идентификаторам. Сохранить many-to-many mapping там, где это подтверждено; не склеивать автоматически две башни с разными сроками и ценами.

Автоматическое сопоставление предлагает кандидатов по идентификаторам, алиасам, району, девелоперу и координатам. Только подтверждённый match даёт право включать сделки в клиентское сравнение. Совпадения только по похожему имени идут в review queue. Координаты центра района не использовать как координаты здания при поиске 1–2 км.

Amenities имеют состояния `existing / planned / unknown`, источник и дату. Обещанный бассейн строящегося проекта не помечать как действующий. Классификация luxury/quality — явная редакционная оценка с критериями, а не факт из маркетингового названия.

### 6.4 Загрузка и свежесть

Начать с выбранных районов/проектов и 24 месяцев продаж, 12 месяцев аренды, справочников проектов/девелоперов; периоды — конфигурация и ограничение MVP, не статистическая гарантия достаточности. Для длинного инвестиционного горизонта расширять историю по необходимости. Полный Units и многолетний Ejari не загружать целиком в браузер.

Хранить checkpoint по каждому источнику, фильтрам и окну; при повторе job результат идемпотентен. Если API допускает стабильную сортировку — использовать её; для изменяющихся offset-страниц выполнять сверку окна после загрузки. Коррекции старых записей учитывать повторным импортом перекрывающегося окна и периодической сверкой прошлого периода. Отсутствие записи на одной странице не означает удаление.

Планировщик: маленькие справочники раз в неделю; выбранные сделки/аренда — ежедневно при квоте и реальной частоте источника; Bayut — по watchlist/запросу с кешем. Это интервалы опроса нашей системы, не обещание свежести источника. Ошибка/429 → backoff, лимит попыток, сохранение последнего успешного состояния. Schema drift → карантин импортированной партии и уведомление.

Каждая метрика показывает `source_as_of`, `fetched_at`, период наблюдений и число записей. «Загружено сегодня» не означает «цена подтверждена сегодня».

## 7. CMA для off-plan: алгоритм v1

### 7.1 Три независимые группы

**A — Ready:** проданные готовые квартиры сходного формата рядом. Ответ: сколько стоил существующий аналог в выбранном периоде.

**B — Off-plan сопоставимого срока:** похожие квартиры и сроки сдачи. Ответ: насколько конкурентоспособен вход среди строящихся альтернатив.

**C — Off-plan ближе к сдаче:** похожий формат, но меньше ожидаемое время до получения объекта. Ответ: какую альтернативу даёт другой срок и другой платежный график.

Внутри каждой группы отдельно показывать DLD registered sales и текущие asking prices/подтверждённые офферы. Их нельзя объединять в одну медиану. Статус сделки оценивать на дату события, если доступна соответствующая классификация; текущий статус проекта не превращает старую off-plan сделку в ready.

### 7.2 Построение выборки

1. Проверить цену и площадь целевого unit type/лота. Не использовать самую дешёвую Studio как цену всей линейки проекта.
2. Найти здания в пределах 1 км, затем до 2 км при недостаточности. Если координаты непригодны — перейти к явно обозначенной community-группе, не рисовать ложный радиус.
3. Исключить физически близкие, но несопоставимые микролокации: другая береговая линия, отделённый магистралью кластер и т.п.; причина ручной географической правки сохраняется.
4. Отфильтровать квартиры того же bedroom type и сравнимого типа площади; стартовый допуск площади ±20%, настраиваемый.
5. Период по умолчанию 6 месяцев; при малой выборке расширить до 12/24 месяцев, явно показать изменение.
6. Исключить неподходящие процедуры, bulk/whole-building/коммерцию, невалидную цену/площадь. Не удалять дешёвые аналоги только потому, что они портят вывод.
7. При наличии надёжных сведений сегментировать по виду, этажу, furnished, branded/unbranded, возрасту/качеству и operating amenities. Если сведений нет — отмечать неопределённость, а не подставлять одинаковые значения.
8. Показать сырые точки сделок, медиану, P25–P75, число сделок и зданий, период, долю пропусков и исключений. Добавить медианы по зданиям, чтобы массовые продажи одной башни были видимы.
9. Сохранить IDs включённых/исключённых записей и причины в `comparable_set`; snapshot используется в контенте и PDF.

Начальные продуктовые пороги: <5 подходящих продаж — только описательный обзор; 5–14 — слабая выборка без заголовка о недооценённости; ≥15 и хотя бы 3 здания — допускается вывод о наблюдаемом ценовом разрыве при остальных проверках. Это консервативные настройки MVP, которые нужно откалибровать, а не доказанные статистические уровни доверия. Сравнение внутри единственного здания допустимо с соответствующей подписью и без притворного охвата района. IQR — диапазон наблюдений, не доверительный интервал цены.

### 7.3 Как назвать результат

`target_psf = target_price / target_area_sqft`

`gap_to_ready = 1 − target_psf / comparable_ready_median_psf`

Если целевой psf = 2 000, а ready median = 2 400, разрыв = 16,67%. Обратная фраза «аналог на 20% дороже» использует другой знаменатель.

Вывод v1: «Цена предложения на X% ниже медианы выбранных зарегистрированных продаж готовых аналогов; выборка N, период …». Разрыв не равен гарантированной недооценённости: отсутствуют текущая аренда во время стройки, срок ожидания, риски и часть характеристик. Строить положительные и отрицательные результаты одинаково; при недостатке данных вывод не формируется.

Не добавлять фиктивные корректировки вроде «+7% за вид», если нет обоснованной методики. На MVP показывать сегменты/различия и ручное экспертное заключение отдельно от статистики. В перспективе возможны модели корректировки с проверкой ошибок на исторических данных.

## 8. Отбор альтернатив и объяснение выбора

Два этапа отбора:

**Eligibility (обязательные условия):** Dubai, квартира Studio–3BR, бюджет, пригодность графика, подходящая стратегия, подтверждённая идентичность, актуальность предложения. Условие неизвестно → `needs_verification`, а не `passed`. Запрет/неподходящее условие уступки исключает вариант из стратегии флипа; он может отдельно рассматриваться для аренды, если клиент готов менять цель.

**Comparison (сравнение прошедших вариантов):** возможность выхода, цена относительно соответствующих off-plan и ready групп, дата/сумма пикового платежа, срок, качество и район. На первом этапе использовать сравнение по отдельным измерениям и помечать доминируемые варианты: дороже, тяжелее по графику и без выявленного преимущества при сопоставимом качестве. Не превращать несопоставимые проекты в единую таблицу псевдоточных рейтингов.

В персональный shortlist по возможности входят: лучший локальный вариант; сопоставимый бюджет в другом районе; похожий проект ближе к сдаче. Если один вариант покрывает две роли, не добавлять слабую квартиру для заполнения третьей колонки.

Каждый вывод содержит:
- «Почему подходит этому клиенту» — 2–3 измеримых аргумента.
- «Чем уступает альтернативе» — существенный компромисс.
- «При каких условиях перестаёт подходить» — цена, платежи, уступка, срок.
- «Что ещё подтвердить» — конкретные недостающие факты.

Взвешенный score допустим позднее с явными, редактируемыми весами и версией формулы. Высокая полнота данных не означает высокую инвестиционную привлекательность; эти показатели всегда раздельны.

## 9. Финансирование: обязательный фильтр до рекомендации

### 9.1 Вводные клиента

Цена-бюджет, наличный капитал сегодня, будущие доступные пополнения по датам (после личных расходов), резерв, средства на сборы, стратегия, допустимые районы/комнаты. Источник и надёжность пополнений фиксируются как декларация клиента; дашборд не выдаёт её за банковскую проверку.

Суммы будущих платежей и доступных денег должны быть в одной временной сетке. Основной расчёт — по датам обязательств; ежемесячный график лишь визуализация. Равномерные «ежемесячные взносы» не подменяют крупный фактический платёж.

### 9.2 Проверка

Для каждой даты t:

`headroom(t) = initial_liquid_cash + cumulative_available_contributions(t) − cumulative_purchase_payments(t) − cumulative_fees(t) − required_reserve(t)`

Если минимум headroom < 0 → дефицит, показать дату и сумму; персональная рекомендация блокируется. Если данные о будущих деньгах/сборах не заполнены → `incomplete`, не зелёный статус. Если есть только 20% и нет ресурсов на дальнейший график → `not_suitable` по зафиксированному правилу владельца.

Не включать ожидаемую перепродажу, будущий рост цены или неподтверждённую ипотеку как гарантированный источник оплаты. Базовая проверка предполагает, что клиент остаётся собственником и выполняет весь договор, включая платёж при сдаче и post-handover при его наличии. Пример с 40% уплаченного капитала в ROI не отменяет этой проверки.

### 9.3 Стресс-сценарии

- Продажа не состоялась до следующего крупного взноса.
- Сдача перенесена на 6/12 месяцев: эти величины — пользовательские стресс-допущения, не прогноз.
- Строительный milestone задержан, но календарные обязательства не сдвинуты автоматически; перемещать только платежи, привязанные договором к событию.
- Сдача произошла, но аренда начинается позже; на первый период необходим отдельный резерв расходов.

Результаты показывать отдельно: baseline funding и stress funding. Слабый стресс-результат требует обсуждения, отсутствие базовых средств исключает рекомендацию. Не выбирать размер резерва за клиента скрыто: ввод обязателен; 0 разрешён лишь как явно выбранное значение с подписью.

## 10. Payment Plan и импорт предложений

### 10.1 Модель графика

Этап: `percent/amount`, `due_date` либо `relative_to_booking` либо `construction_milestone` либо `handover + offset`; точность/источник даты обязательны. Booking deposit — часть цены или отдельная сумма по документу; не учитывать дважды. Промо «DLD waiver», cashback и скидка хранятся отдельно с условиями. Не вычитать скидку повторно, если цена уже net.

Проверить сумму платежей к цене; проценты 100% с допустимой погрешностью округления. «20/80» без пояснения, когда платятся 80%, не является полноценным графиком. Для research можно показать предварительную структуру; для клиентской пригодности нужен проверенный график.

### 10.2 Импорт Excel/CSV

MVP: загрузка → выбор листа → привязка столбцов → preview → ошибки → подтверждение → новая offer revision. Сохранять файл, checksum, дату получения, проект/башню, номер лота, тип, вид/этаж, площадь и единицу, цену net/list, валюту, availability, plan ID, срок актуальности, автора подтверждения. Номер 0102 сохранять строкой.

Сообщения: сначала вставка текста и ручная форма. PDF/OCR и AI-extraction — последующая помощь, всегда с подтверждением каждого критического поля. Не выполнять макросы/формулы из загрузок; проверять размер, расширение, MIME, не запускать вложенное содержимое. Различать reported available, unavailable и unknown. Истечение проверки не означает sold.

По умолчанию предложение старше 48 часов при финализации PDF просит повторное подтверждение; это внутреннее правило свежести, не обещание срока действия цены. Агент может подтвердить по новому сообщению с evidence. Исторический research с датой может оставаться доступным независимо от срока оффера.

## 11. Прибыль при уступке и доходность на капитал

### 11.1 Основные обозначения

P — полная договорная цена; A(t) — сумма, уже уплаченная в счёт цены к моменту выхода; B(t) — непогашенная цена; C(t) — другие внесённые расходы; S(t) — полная предполагаемая цена перепродажи; E(t) — расходы выхода. При простом договоре B = P − A, но сверять с реальным балансом.

Для сделки, где остаток обязательства принимает покупатель:

`seller_receipt = S − B − E`

`invested_cash = A + C`

`net_profit = seller_receipt − invested_cash`

`return_on_invested_cash = net_profit / invested_cash`

Это доходность за срок сделки. Термин rental cash-on-cash используем отдельно для ежегодного денежного потока от аренды. Внутри системы считать датированные cash flows; если по договору продавец должен временно погасить больше баланса до передачи, показать дополнительную потребность в деньгах и пересчитать капитал. Различать полную стоимость квартиры и сумму, получаемую продавцом за его права/внесённые платежи; API/Excel могут обозначать их неодинаково.

### 11.2 Числовой fixture — только демонстрация арифметики

P = 2 000 000; A = 800 000 (40%); B = 1 200 000. Рост полной цены на 15% даёт S = 2 300 000. Без расходов прибыль = 300 000, доходность к A = 37,5%.

Если дополнительно C = 80 000 и E = 50 000 (вымышленные фиксированные расходы, не ставки законодательства), тогда:

- seller receipt = 1 050 000;
- invested cash = 880 000;
- net profit = 170 000;
- доходность на капитал = 19,318…% за период.

Если S падает до 1 800 000 при тех же расходах, net profit = −330 000, return = −37,5%. Прибыль и риск на частично внесённый капитал усиливаются симметрично.

### 11.3 Дополнительные результаты

- Цена безубыточности при фиксированных расходах: `P + C + E`. Если выходные расходы включают `s × S + fixed`, то `S_break_even = (P + C + fixed) / (1 − s)` при 0 ≤ s < 1.
- Прибыль AED, капитал AED, срок, ROI за период; величины не смешивать в один показатель.
- XIRR после появления надёжных дат: решать NPV=0 по датированным потокам; учитывать отсутствие/несколько решений и не показывать выдуманное число. Одна и та же прибыль за 6 месяцев и 3 года не равнозначна.
- Комиссии/сборы/waiver — редактируемые правила с датой, плательщиком, базой начисления и источником; юридические ставки не зашивать без актуальной проверки.
- Любой unknown cost отображать отдельно. Пока существенные расходы не заполнены, подпись «чистая прибыль» запрещена; показывать «результат по учтённым расходам».

## 12. Exit Strategy: допустимые точки выхода и сценарии

Система строит сетку дат относительно подтверждённого ожидаемого handover: −12, −6, −3 месяца и сдача; исключает прошедшие/неподходящие даты. Эти точки — стартовая конфигурация, не доказанные оптимальные окна. Сдача далеко → добавить даты крупных платежей, если они важны. Сценарий аренды на 12 месяцев после сдачи используется как продолжение владения, а не обязательное продление первичного инвестиционного горизонта.

Для каждой даты рассчитывать:

| Поле | Значение |
|---|---|
| Legal/contract eligibility | Процент оплаты, NOC, минимальное время/этап, сборы, актуальность подтверждения |
| Funding | Сколько нужно внести и какой запас остаётся без продажи |
| Economics | Остаток, расходы, break-even, прибыль/ROI по 3 ценовым сценариям |
| Market context | Зарегистрированные сделки релевантного сегмента, конкурирующие запуски/сдачи, покрытие |
| Uncertainty | Неизвестные условия, слабая выборка, потенциальный перенос |

Правила уступки: `allowed / prohibited / conditional / unknown`. Unknown не означает allowed. Нельзя автоматически предположить универсальные 30%/40% и одинаковые правила всех девелоперов. Проверить, что порог оплаты выполнен к выбранной дате и требуется ли доплата для NOC.

На MVP будущая цена — набор прозрачных допущений агента. Можно показать, какие исторические сравнения использованы как ориентиры, но не переносить ready gap целиком в ожидаемую прибыль. Расчёты по графику автоматические; будущая рыночная цена не становится фактом от автоматизации.

Выбор лучшего сценария: сначала исключить непригодные даты, затем сравнить net profit, ROI/XIRR, капитал и чувствительность. Не объявлять максимальный ROI единственной целью; более ранний выход может давать меньшую прибыль и быть хуже по доступности сделки. Результат: «При заданных ценах и условиях предпочтительно окно …; при падении цены/изменении уступки вывод меняется». Автоматически показывать и вариант не продавать.

Если нет данных для вероятности продажи, не писать «вероятность выхода 85%». DLD-объём сделок — proxy активности, не доказанный срок продажи. Отсутствие объявления в следующем API снимке не означает состоявшуюся продажу.

## 13. Developer Track Record и строительство

Для каждого проверенного проекта сохранить:

- Юридического девелопера и отдельно связь с брендом, фазу/башню.
- Первоначальный обещанный срок из датированного документа; при квартале сохранять диапазон и правило использования конца квартала.
- Каждое изменение обещанного срока как событие, а не overwrite.
- Подтверждённые фактическую строительную готовность и передачу ключей раздельно.
- Дату/источник каждого наблюдения о проценте строительства.
- Документы проверки escrow: что именно проверено, дата, источник; наличие банка/номера и текущий статус счёта раздельно.

Задержка рассчитывается только при сопоставимых исходном и фактическом событиях. `late_days = max(0, actual_handover − original_promised_date)`. Отдельно можно показывать signed difference для досрочной передачи. Завершённый проект без исходной даты не включать в среднее. Незавершённый после обещанной даты — отдельный overdue факт, не нулевое наблюдение в среднем.

По умолчанию показывать последние 5 **пригодных для расчёта** завершённых проектов, правило отбора, список и покрытие: например, «есть исходные документы по 5 из 18». Медиана, среднее, диапазон задержек; завершённые и незавершённые проекты отдельно. Не выдавать эту выборку за статистику всего бренда.

Опубликованная схема DLD Projects описывает ожидаемые сроки и банк escrow, но не гарантирует наличие первоначальных обещаний/фактической передачи или активного статуса счёта. Без подтверждения поля — «нет данных». Проект active и процент 100% сами по себе не равны `escrow_active` или передаче каждой квартиры.

На MVP — прозрачная карточка фактов и предупреждений. Единый рейтинг надёжности 0–100 отложить до достаточного покрытия и утверждённой методики. Начать собственное накопление истории с первого импорта; оно не восстанавливает автоматически прошлые изменения.

## 14. Конкурирующее предложение и инфраструктура

Добавить таблицу соседних/сопоставимых проектов: формат квартир, ожидаемый срок, процент строительства, известное число единиц и его источник, диапазон цен, платёжные условия. Группировать ожидаемые сдачи по кварталу с вариантом сдвига сроков.

Если количество units неизвестно — показать число наблюдаемых проектов и покрытие, не выводить точное количество будущих квартир. Число зарегистрированных продаж не делить на units для «распродано 85%» без полной проверенной базы доступного инвентаря и уникальных единиц.

Инфраструктурный объект: анонсирован, строится, действует; официальный источник, дата, оценка доступности. Открытие метро/моста не переводить автоматически в +X% к цене. На MVP это объясняющий контекст и тема контента; причинный коэффициент роста требует отдельного исследования.

Качество для проживания: планировка, балкон/полезная площадь, парковка, walkability/доступность, шум/стройка вокруг, вид и риск его изменения, operating versus planned amenities. Наблюдения агента подписываются как наблюдения с датой. Не считать время маршрута равным расстоянию по прямой.

## 15. Аренда после сдачи

Использовать зарегистрированную годовую аренду похожих готовых квартир. Новые и продлённые договоры отдельно; multiple-property contracts исключать из per-apartment метрик, если корректное распределение суммы не подтверждено. Не делить одну сумму на число строк договора автоматически.

`gross_yield = annual_potential_rent / purchase_price`

`effective_rent = annual_potential_rent × (1 − vacancy_rate)`

`NOI = effective_rent − service_charges − management − maintenance − other_operating_costs`

`net_yield_on_cost = NOI / total_acquisition_and_fitout_cost`

Первый неполный год после handover считать по реальному сценарному старту аренды. Если источник уже содержит чистый доход/простой, не вычитать повторно. Для fees, зависящих от собранной аренды, зафиксировать базу начисления. Service charge аналога — допущение, а не тариф нового дома; возможное пересечение reserve fund и service charge не дублировать.

Ипотеку в MVP не предполагать. Если позже добавлено финансирование: rental cash-on-cash = годовой денежный поток после debt service / фактически вложенный собственный капитал; обязательства по post-handover платежам учитывать в общей кассе отдельно. Арендная модель не должна скрывать финансовый дефицит.

## 16. Студия контента RU/AR

Каждый `content_brief` связывается с analysis snapshot: вопрос аудитории, целевой клиент, утверждения, supporting metric IDs, сравнения, неизвестное, CTA. Один источник цифр для обоих языков.

Структура рилса 45–75 секунд, редактируемая:
1. 0–5 с: конкретный вопрос/наблюдение, без выдуманного дефицита.
2. 5–20 с: цена и контекст/альтернатива.
3. 20–40 с: график платежей, преимущество или условие выхода.
4. 40–55 с: один существенный компромисс.
5. Завершение: «Напишите [код проекта] — сравним 2–3 варианта под ваш бюджет».

Шаблоны графиков: сравнение AED/ft² с интервалами; совокупные платежи против средств клиента (без личных данных); прибыль по сценариям; handover timeline; сравнение 3 вариантов. Публичные графики не содержат имени, бюджета или внутренних заметок реального клиента без отдельной необходимости/разрешения.

Экспорт SVG/PNG с кириллицей и арабским shaping/RTL, фон прозрачный или фирменный; шаблоны 1080×1350 и 1080×1920, отдельно компактная overlay-карточка. Размеры — выбранные форматы производства, не обещание требований платформы. Настраиваемая безопасная область для лица/субтитров. На графике: единица, as-of, источник, выборка/период, факт или сценарий. Цифры нельзя обрезать в небольшом мобильном кадре. Для арабского текста рекомендуем разговорный стиль автора; названия и числа не переводить так, чтобы менялась идентичность проекта.

AI optional: на основе whitelisted фактов предлагает хук/текст/перевод, не считает финансы и не дополняет пропущенные характеристики. Каждое числовое утверждение должно ссылаться на metric ID. Любое изменение сценария обнуляет редакционное утверждение производных материалов. Автоматическая публикация не входит в MVP.

## 17. Персональный PDF: структура и первый экран

Отчёт 6–8 основных страниц + приложение при необходимости:

1. **Персональный вывод:** задача клиента; 2–3 варианта; почему один предпочтителен по согласованным критериям; ключевой компромисс. Цена входа, наблюдаемый разрыв, необходимый капитал, результат базового сценария — с подписями.
2. **Сравнение:** конкретные лоты/типы, net price, площадь/вид, срок, график, применимость уступки, свежесть.
3. **CMA:** ready/off-plan группы раздельно, распределения, N и периоды, правила исключения и различия аналогов.
4. **Финансирование:** платежи против доступных средств, пик, резерв, проверка «не продали до сдачи».
5. **Выход:** допустимые окна, break-even, результат по сценариям с расходами, отрицательный сценарий.
6. **Застройщик/окружение:** проверенная история и покрытие, стройка, конкурирующие сдачи, неизвестное.
7. **Аренда после сдачи и следующий шаг:** диапазон допущений, expenses, конкретные вопросы к представителю застройщика.
8. **Источники и методика:** версия, даты, документы, контакт агента/агентства и необходимые реквизиты для согласованного рекламного формата.

Первый экран не заполняется всегда положительной прибылью или скидкой. Возможные формулировки: «Вариант A требует меньше капитала до сдачи при сопоставимом бюджете»; «Цена на X% ниже выбранной ready-выборки; срок ожидания Y»; «Базовый сценарий даёт X AED по указанным допущениям». При неизвестных существенных расходах — без слова «чистая». При отсутствии преимущества — честный вывод.

Валюта расчёта AED. USD по желанию только как дополнительное отображение с указанным курсом/датой или явно заданным пользователем курсом; не смешивать валюты в формулах. Цифры RU/AR PDF идентичны; locale меняет оформление.

PDF генерируется из immutable snapshot: offer revisions, scenario inputs, included comparable IDs/values, формулы/методика, заключение, evidence manifest, template version. Хранить JSON, PDF и hash; версия «отправлено» неизменяема. Изменение данных создаёт отчёт v2 с перечнем изменений. Готовый файл скачивается агентом для ручной отправки; CRM-автоматизация и публичные ссылки позже.

## 18. Статусы и правила публикации

Разделить статус исследования, предложения и артефакта:

- `research`: discovered → mapped → analysed → editorial_reviewed → content_ready; можно с отсутствующим developer offer, если конкретные неподтверждённые условия не выдаются за факт.
- `offer`: imported → parsed → reviewed → confirmed → stale/unavailable; unknown validity отдельно.
- `client_analysis`: draft → funding_checked → terms_checked → reviewed → ready; блокировки показываются с причиной.
- `artifact`: draft → approved → exported → sent/published → superseded; уже отправленный файл не исправляется незаметно.

Для клиентской рекомендации обязательны: подтверждённый лот/цена/график; свежесть; funding pass; проверка уступки для flip; источник ключевых характеристик; учтённые/неизвестные расходы; утверждённый вывод. Недостаточный CMA может не мешать описательному отчёту, но блокирует заголовок о недооценённости. Отсутствие escrow-status не превращать в отрицательный статус счёта и не скрывать.

Content readiness не равна offer readiness. Это важная разница с предыдущим планом, который требовал полные документы слишком рано.

| Слой | Выбор | Зачем |
|---|---|---|
| Web | Next.js App Router + TypeScript, Node runtime | Закрытый рабочий интерфейс, серверный доступ к БД |
| UI | Tailwind + shadcn/ui | Таблицы, формы, drawers, доступность |
| Таблицы | TanStack Table, server-side pagination | Большие выборки не отправлять целиком в браузер |
| Графики | Recharts/SVG; окончательно одна библиотека после export spike | Читаемые сравнения и воспроизводимый экспорт |
| Формы/контракты | Zod + React Hook Form | Validation, nullable и ошибки источников |
| Данные | PostgreSQL + PostGIS | Транзакции, версии, поиск в радиусе по проверенным точкам |
| ORM | Drizzle + SQL migrations | Одна схема и явные SQL для агрегатов/географии |
| Финансы | Чистые TypeScript-функции + Decimal arithmetic | Один расчёт для UI, PDF, сценариев и тестов |
| Auth | Auth.js, Google OAuth, allowlist одного пользователя | Без собственной парольной системы/публичной регистрации |
| Jobs | Node/TypeScript worker + Postgres job queue (например pg-boss) | Retry, durable jobs, без обязательного Redis |
| PDF/PNG | Playwright Chromium worker | HTML print/PDF, PNG графиков и RTL |
| Файлы | Закрытый persistent volume, off-server encrypted backup | Excel, evidence, snapshots, экспорты |
| Deploy | VPS + Coolify, Docker, reverse proxy HTTPS | Использовать существующую инфраструктуру |
| AI | Опциональный серверный адаптер к выбранному провайдеру | Текст/перевод после проверенных вычислений; лимит расходов |

Версии пакетов выбрать из совместимых стабильных на старте, зафиксировать lockfile и Docker image. Не писать план под неопределённый `latest`. Пакет auth/jobs/export подтвердить минимальным интеграционным spike; не менять весь стек без выявленной причины. Для одного пользователя Postgres достаточно; Redis, ClickHouse, отдельный Python-сервис и vector DB пока не нужны.

Приватные запросы не кешировать публичным CDN и не делать SSG для пользовательских PDF. Server Components читают через авторизованный DAL. Route Handlers/Server Actions проверяют доступ в каждом действии. Middleware/Proxy и `noindex` не заменяют авторизацию.

Долгие импорты и PDF выполняются worker. Вызов POST возвращает job ID, UI показывает прогресс. Worker и web используют одни domain-функции. Лимит PDF-параллельности 1 в начале; импорт также ограничен. Не запускать полный Chromium на каждый запрос без ограничения.

| Группа | Таблицы / важные связи |
|---|---|
| Источники | source_connection, source_policy, ingestion_run, source_record_revision, schema_version |
| География | area, community, building_location; координата + precision + source |
| Каталог | developer, developer_brand_link, project, phase, building, unit_type |
| Связи | external_identity, project_source_match, entity_alias; many-to-many where reviewed |
| Характеристики | amenity_observation, project_attribute_observation; planned/existing/unknown |
| История | construction_observation, handover_event, escrow_evidence, infrastructure_event |
| Рынок | transaction_fact, rent_contract_fact, service_charge_fact; raw keys и source revision |
| Материалы | document, evidence, statement; rights/internal_only/export_allowed/unknown |

| Клиенты | client_brief, funding_contribution, reserve_rule; PII отдельно от research |
| Анализ | analysis_revision, comparable_set, comparable_member, eligibility_result, scenario, cashflow, metric_snapshot |

| Эксплуатация | job, audit_event, api_usage, settings_version |

Индексы: source+external key, project/date/type/bedrooms для facts, GIS по точкам, analysis/revision для snapshots. Уникальность исключает повтор импорта. Raw и normalized версии хранятся отдельно; pinned reports сохраняют необходимые факты и значения даже после очередного импорта. Архивировать неиспользуемые большие raw payloads по настраиваемому сроку; evidence утверждённых отчётов не удалять автоматически.

Пример контракта вычисления:

```ts
type EvidenceState = 'verified' | 'reported' | 'assumed' | 'missing' | 'conflict';
type Metric<T> = {
  value: T | null;
  unit: string;
  state: EvidenceState;
  asOf: string | null;
  sourceRevisionIds: string[];
  methodologyVersion: string;
  sampleSize?: number;
  limitations: string[];
};
```

Нулевая прибыль и неизвестная прибыль — разные значения. Report engine получает готовый AnalysisSnapshot, не самостоятельно делает API-запросы и не пересчитывает цифры иной формулой.

## 22. Защита, хранение и права

Один аккаунт, MFA на провайдере входа, access check для каждого API/download, private cache headers, HTTPS, лимиты upload. Ключи только env сервера; в логах не выводить токены, полный brief/телефон. Файлы вне публичной директории. Резервная копия БД и документов вне VPS; испытать восстановление. Для демонстраций использовать вымышленные клиентские briefs.

Не переносить агентские телефоны/контакты из внешнего API в маркетинговую базу. Минимальные собственные контакты клиента хранить только если они нужны для процесса. Для LLM отправлять проверенные агрегаты и нужные выдержки, а не все личные/договорные документы по умолчанию; удалять персональные сведения.

У DLD-наборов и материалов застройщика сохранять применимые условия использования. BayutAPI и RPPI условны по результатам проверки прав; система продолжает работать с доступными разрешёнными источниками. Через агентство установить применимость рекламных разрешений/QR к конкретным форматам видео/PDF. Это реальная задача процесса публикации, а не причина останавливать разработку вычислений на fixtures.

## 24. Проверки, которые действительно необходимы

### Финансы

1. P=2m, paid=40%, premium=15%, zero costs → 300k profit и 37,5% ROI.
2. Те же числа с C=80k, E=50k → 170k и 19,318…%; S=1,8m → −330k и −37,5%.
3. Только 20% initial cash, будущих средств нет → funding fail, даже если flip scenario прибыльный.
4. Среднемесячный доход покрывает сумму, но деньги приходят после взноса → fail на конкретную дату.
5. Неизвестный handover payment/expense → incomplete, не pass.
6. Post-handover обязательства не исчезают при ограничении chart на дату сдачи.
7. Booking внутри цены, net discount и waiver не учитываются дважды.
8. NOC threshold/bridge funding меняет доступность даты и капитал.
9. Отрицательные returns корректны; XIRR с некорректным набором потоков не показывает случайный результат.

### Данные и CMA

- Корректное sqft/m², null/studio, сопоставимый тип площади.
- Нельзя соединить две фазы только по одинаковому маркетинговому имени.
- Районный центр не проходит как координата дома; fallback явно подписан.
- Повторная загрузка не создаёт дубли; корректировка source record не меняет уже отправленный PDF.
- Нельзя включить mortgage/gift/whole building в apartment median.
- Old off-plan sale не становится ready по нынешнему статусу проекта.
- Новые/renewed rents и multi-property договоры не смешиваются некорректно.
- Нет выборки → null, а не 0 AED/ft² или 100% «скидки».

### Экспорт и доступ

- RU/AR snapshot даёт те же суммы; shaping/RTL, единицы, числа и имена корректны.
- PDF/PNG не содержат служебные notes, контакт другого агента или чужой клиентский brief.
- При смене плана оплаты approved draft становится устаревшим, старая отправленная версия остаётся.
- Файл/API недоступен без сессии; загрузка и PDF renderer не получают произвольный доступ к внутренней сети.
- Реальные PDF просмотрены на телефоне/компьютере: графики/источники читаются, строки не режутся.

Не писать сотни тестов на верстку кнопок. Приоритет: финансы, идентификация, выборки, снимки отчётов и авторизация.

## 25. Эксплуатация и бюджет

Лимит 200 AED трактовать как месячный потолок дополнительных расходов при уже оплаченном VPS. Плановые лимиты, не рыночные котировки: backup/storage до 40; AI до 30; domain amortization до 10; API/резерв до 120 AED. Общий 200. Если инфраструктура уже включает backup/domain, остаток не нужно тратить. Платный Bayut-доступ и права не считать заранее бесплатными навсегда.

На первом запуске проверить RAM/disk: PostgreSQL + Chromium требуют запаса; исходная инженерная оценка для пилота — около 4 GB RAM и SSD, но размер определяет реальное профилирование и имеющаяся нагрузка VPS. Если ресурс мал, сначала manual print и ограниченный импорт. Счётчики API, общий лимит расходов, batch size, PDF concurrency=1. Никаких API-запросов при каждом движении слайдера.

Эксплуатационные цели, проверяемые на пилоте: открытие кешированной карточки около 2 секунд, пересчёт сценария до 300 мс для умеренного числа cash flows, PDF через очередь около 30 секунд. Это целевые значения, не обещание без измерения. Job failure не должен ломать доступ к последней успешной версии.

Еженедельно: 1–2 подробных разбора, 1–3 рилса по фактической доступности; проверка stale offers только по активным клиентам; просмотр data-health. Метрики: время анализа, число исправленных неверных matches, доля подтверждённых утверждений, количество PDF-запросов и разговоров по каждому ролику. Просмотры отдельно от квалифицированных лидов и сделок.

## 26. Развитие после MVP

1. Накопление истории офферов, планов, сроков и construction snapshots; улучшение shortlist на реальных запросах.
2. Полуавтоматическое извлечение PDF/сообщений; агент подтверждает поля.
3. Прогнозные эксперименты: point-in-time данные, известные на дату прогноза; временное разделение train/test; holdout проектов; сравнение с простыми baseline; MAE/ошибки диапазонов, покрытие, отсутствие look-ahead и survivorship bias. Даты сдачи для обучения должны быть достоверны. Если модель хуже простого baseline — не публиковать прогноз.
4. Только после проверки — вероятностные диапазоны цены/сроков и сценарная оптимизация; никогда не называть их гарантией. Общий индекс RPPI не является достаточным набором для обучения цены конкретного проекта; его применимые права — отдельный вопрос.
5. Ready-квартиры как ассортимент: состояние, занятость/договор аренды, фактические расходы, ипотека, transfer costs, inspection. Текущие ready comps уже подготовят часть справочников.
6. Abu Dhabi — отдельные источники, процедуры и справочники; Dubai-правила не переносить молча.
7. Публичный сайт на одобренных агрегатах, когда собственная методика, контент и спрос подтверждены.

## 27. Инструкция для LLM-исполнителя

Этот документ является продуктовым контрактом. Реализовывать по фазам 0–7 с сохранением решений в `docs/decisions.md`. Не считать недоступное поле существующим, не выдавать mock API за подключение.

Для каждой задачи:
1. Указать фазу, используемые fixtures/контракты и конкретный критерий завершения.
2. Реализовать минимальный законченный путь; не добавлять новый сервис без причины.
3. Проверить расчёты/данные/доступ соответствующими тестами из раздела 24.
4. Показать, какие поля реальны, какие заглушки и какие проверки остались.
5. Сохранить миграции, команды запуска и короткий handoff следующей задаче.

Обязательные доменные модули: `buildComparableSet`, `evaluateFunding`, `validateTransferEligibility`, `buildExitCashflows`, `calculatePeriodReturn`, `calculateBreakEven`, `calculateRentalScenario`, `buildDeveloperTrackRecord`, `freezeAnalysisSnapshot`.

Финансовые модули — детерминированные функции без LLM внутри. Одна реализация для UI/экспортов. Формулы, пороги и методика версионируются. Модель не выбирает оптимистические параметры, чтобы сделать результат привлекательнее.

Фаза 0 может завершиться выявлением отсутствующего источника/поля: это документируется и функция получает честное состояние unknown. Работа над независимыми частями продолжается. Вопросы владельцу задавать по конкретному конфликту бизнес-правил, а не по выбору цвета кнопки.
